## 0. Rules for agents

1. **Only cited requirements are in scope.** Implement exactly what your task cites — whole requirements, or only the named ACs where it cites `REQ-X/ACn` — plus the §3 invariants. Do not implement later phases early.
2. **Acceptance criteria are the contract.** A requirement is met only when every AC is demonstrably satisfied by its verification method: `(T)` test, `(T-HW)` hardware test, `(I)` inspection, `(D)` demonstration, `(A)` analysis.
3. **Never weaken the oracle.** Do not edit this file, gate definitions, protected acceptance tests, or fixtures to make work pass (REQ-TST-007, REQ-TST-012).
4. **Blocked is a valid outcome; faking is not.** If an AC is ambiguous, contradictory, or impossible, stop and write a `BLOCKED:` entry (template in `tasks.md`). Stubs, placeholders, special-casing test inputs, and hardcoded outputs are defects (INV-13).
5. **Show evidence, not claims.** Record the commands you ran and their output in the phase evidence file.

## 1. Conventions

### 1.1 Requirement language
Acceptance criteria use **EARS** sentence patterns (Easy Approach to Requirements Syntax), with the keywords in capitals:

| Pattern | Template |
|---|---|
| Ubiquitous | The ‹component› SHALL ‹response› |
| Event-driven | WHEN ‹trigger›, the ‹component› SHALL ‹response› |
| State-driven | WHILE ‹state›, the ‹component› SHALL ‹response› |
| Unwanted behavior | IF ‹condition›, THEN the ‹component› SHALL ‹response› |
| Optional feature | WHERE ‹feature/config›, the ‹component› SHALL ‹response› |
| Preserved behavior | the ‹component› SHALL CONTINUE TO ‹existing behavior› |

**Priority** sits in each requirement's header: **MUST** (gates the phase), **SHOULD** (skip only with a written justification in the gate evidence), **MAY** (optional). An AC written with "SHOULD" is SHOULD-level even inside a MUST requirement.

Components are named consistently: *the repository, CI, the config loader, the daemon, the proxy, the scheduler, the oracle, the runtime manager, the telemetry manager, the benchmark lab, the TUI, the CLI*.

### 1.2 Identifiers

| Form | Meaning |
|---|---|
| `INV-nn` | Invariant — applies to every task, always |
| `REQ-<AREA>-nnn` | Requirement. `REQ-PRX-002/AC2` names one acceptance criterion |
| `NG-nn` / `ASM-nn` | Non-goal / assumption |
| `DEC-nn` / `OQ-nn` | Normative decision / open question |
| `BD-nn` | Baseline defect found at `c89f278` |

Areas: `MIG` migration · `REPO` repository · `CI` · `CFG` configuration · `SEC` security · `ERR` errors · `PRX` OpenAI proxy · `PROC` process control · `ARCH` architecture · `DMN` daemon · `CLI` · `TUI` · `RT` runtime backends · `PROF` profiles · `TEL` telemetry · `ORC` oracle · `SCH` scheduler · `BEN` benchmark lab · `MOE` MoE lab · `REM` remote serving · `SVC` service & recovery · `TST` testing · `DOC` documentation & spec process · `NFR` non-functional · `VAL` flagship validation · `REL` release.

IDs are never reused. Retired IDs are listed in Appendix I.

### 1.3 Tags
- `[PROP]` — a universally quantified property. Test it with property-based tests (`proptest`), not only examples.
- `[HW]` — needs the reference host (Pop!_OS, Ryzen 7 7700, 32 GB DDR5, RTX 3060 12 GB).
- `[HUMAN]` — needs an operator action or sign-off.

### 1.4 Traceability
- A task's **Reqs** line cites whole requirements (`REQ-SEC-002` = every AC) or single ACs (`REQ-SEC-002/AC3` = that AC only). An AC is **due** at the first phase of any task that covers it. The generated `Tasks:` field shows the scopes, e.g. `T1.9 (AC3), T4.1, T9.2`.
- Every test that verifies an AC carries its ID in the test name or a comment, e.g. `/// Verifies: REQ-PRX-002/AC2` (REQ-TST-016). Rust tests, Python/shell test scripts, and CI workflow steps count; Markdown never does.
- Every commit cites the task and requirement IDs (`Task: T1.11`, `Refs: REQ-PRX-002`).
- Backward traceability: each requirement names its source in its meta line (`Src:`, or an `INV`/`DEC`/`BD` reference) or inherits its area's row in Appendix G.
- `spec_lint.py` enforces these rules mechanically (REQ-DOC-006); `--sync` regenerates the `Verify`, `Phase`, and `Tasks` fields.

## 2. Scope

**Target identity (BP §1):** Saltnitor is a hardware-aware runtime control plane and tuning laboratory for local llama.cpp inference. It manages model residency, monitors host pressure, benchmarks runtime configurations, and exposes local models to OpenAI-compatible clients and coding agents.

**Division of responsibility (TP §1):** Saltnitor manages the runtime. llama.cpp executes the model. Qwen reasons. The coding agent controls tools and the project. Tailscale connects the machines.

## 3. Invariants

These are BP §30 design rules plus TP principles, restated so they can be checked. Every task preserves all of them. "Enforced by" names the mechanism; a remediation message must accompany every automated failure (REQ-CI-008).

| ID | Invariant | Enforced by | Source |
|---|---|---|---|
| INV-01 | **Inference belongs to llama.cpp.** Saltnitor never executes tensors, samples tokens, or transforms model output. | review rubric (REQ-TST-015); byte-exact tests (REQ-PRX-003) | BP §30.1, §14 |
| INV-02 | **No fake capabilities.** Every capability comes from a probe of the actual runtime or an explicit override recorded with provenance `override`. | fixture tests (REQ-RT-005) | BP §30.2 |
| INV-03 | **Unsupported settings are rejected or hidden** — never passed through silently, never shown as working. | REQ-RT-008 tests | BP §30.3 |
| INV-04 | **Performance claims need stored evidence.** Every performance number in TUI/CLI/API/exports/docs traces to a stored record ID. No literal performance numbers in `src/` outside tests/fixtures. | invariant scan; REQ-BEN-004 | BP §30.4, §20 |
| INV-05 | **Load success is not stability.** A configuration is `stable` only after it survives its validation workload. | REQ-ORC-014 tests | BP §30.5; TP §18 |
| INV-06 | **Remote exposure is explicit.** No non-loopback listener exists without explicit configuration; detecting an address never causes binding. | REQ-REM-002/003 tests | BP §30.6 |
| INV-07 | **Raw llama-server stays private** (loopback only). | REQ-REM-005 check | BP §30.7; TP §37 |
| INV-08 | **Streaming semantics are preserved** end to end. | REQ-PRX-002/003 tests | BP §30.8 |
| INV-09 | **No kill by name.** Signals target exact PIDs or pidfds. | invariant scan | BP §30.9 |
| INV-10 | **Invalid configuration is never silently replaced** by defaults or partial data. | REQ-CFG-003 tests | BP §30.10 |
| INV-11 | **No coupling to Qwen or one fork.** The literals `qwen`/`codacus` (case-insensitive) appear in `src/` only in the fork's backend module and the parameter-registry data; elsewhere only in tests/fixtures/examples/docs. | invariant scan | BP §30.11; TP §42 |
| INV-12 | **No unvalidated production runtime change.** Saltnitor never pulls, builds, or edits runtime channel directories. Changing the stable build needs a passing validation record. | invariant scan (no git/cmake/make in `src/`); REQ-RT-013 | BP §30.12 |
| INV-13 | **Tests do not stand in for functionality.** No test-only branches in production code, no outputs keyed to test inputs, no stubs or placeholders behind passing tests. Every gate includes runtime-surface checks. | review rubric (REQ-TST-015); CI lints (REQ-CI-007) | BP §30.13 |
| INV-14 | **Reproducibility tuple.** Every benchmark run, validation record, observed-memory record and crash record stores runtime fingerprint (commit SHA + binary hash), model file hash, resolved profile (incl. effective env), and hardware/driver identity. | DB NOT NULL constraints (REQ-BEN-003) | BP §30.14; TP §5 |
| INV-15 | **Every optimization is disable-able**, including ones the runtime enables by default, and a baseline profile can always be derived. | REQ-PROF-006 tests | BP §30.15; TP §13 |
| INV-16 | **No secrets** in source, logs, exports, or (schema v2) plaintext config. | secret scan; REQ-SEC-006 tests | BP §4.4 |
| INV-17 | **No hardcoded tuning values.** Model/runtime tuning numbers come from profiles or experiments; the generic safety defaults in §6 are the only numeric defaults. | review rubric | TP §24 |
| INV-18 | **Truthful values.** Anything not measured or received shows as `null`/`n/a` with a reason — never `0` or a guess. | REQ-TUI-006 tests | BP §20; BD-18 |

## 4. Decisions and open questions

### 4.1 Decisions (normative)

| ID | Decision | Rationale |
|---|---|---|
| DEC-01 | BP §27 migration order and §34 priority order are authoritative. TP §39 phases map onto them (Appendix G). | BP is the implementation spec; TP starts with runtime work, which BP puts after hardening. |
| DEC-02 | The residency scheduler (BP §13; roadmap v0.6) is built in **P6, before the benchmark lab**. | Lab runs need exclusive leases; "a swap never terminates an active request" is a correctness property. |
| DEC-03 | **One active runtime process tree per host.** With `native_router`, Saltnitor runs `llama-server` in router mode (`--models-preset <generated>`, `--models-max 1`, and `--no-models-autoload` when supported). The preset holds every servable profile of that runtime that shares the same effective process env. Without a router, it uses single-model mode (`-m … --alias <profile-id>`). The **resident unit** is (runtime id, effective-env hash, profile id). | Unifies BP §8.1 `start(profile)` with the existing router design (TP §8). Upstream `--models-max` is not race-safe under concurrent requests (llama.cpp #20137), so Saltnitor serializes all loads. |
| DEC-04 | **TOML profiles are the single source of truth.** The router preset INI is generated into the state dir. A hand-written `router.ini` is imported once by `config migrate`. | Removes the hardcoded path (BD-06) and dual truth. |
| DEC-05 | `runtime_process_mode = "managed"` is the default. `"external"` (systemd-managed llama-server) stays supported, and features it cannot offer are reported as unavailable. A v1 config without a runtime executable falls back to `external` (REQ-SVC-001/AC2). | BP §22 |
| DEC-06 | Config schema v2 follows BP §10 sections. TP §29 `[control] bind = "tailscale"` becomes `[remote] mode = "tailscale"`. The TP §7 layout (`profiles/*.toml`, `workloads/*.json`) is supported. | One schema |
| DEC-07 | Auth is on by default in schema v2 and may be disabled only when every listener is loopback or UDS. In P1 (schema v1), a configured token is enforced on every protected route. | BP §4.3; TP §37 |
| DEC-08 | Error bodies are a superset of the OpenAI error object (`message`, `type`, `code`) plus `details` and `request_id`. Appendix B is normative. | BP §23; client compatibility |
| DEC-09 | Persistence uses SQLite (bundled engine) with versioned migrations; JSON export/import is supported. | BP §19.2 |
| DEC-10 | The admin API is served on UDS (peer-credential auth) and loopback HTTP (admin token), never on remote listeners unless `remote.allow_admin = true`. Remote administration goes over SSH. | BP §4.3, §6.2; TP §35 |
| DEC-11 | Remote serving is built and gated in P9 with any stable profile. The production agent profile is chosen and promoted in P10, before it is served remotely as production. | TP §42 steps 8–10 vs BP Phase 8 |
| DEC-12 | Lab runs (benchmarks, traces, tuners) hold an exclusive **lab lease**. By default, inference during a lab run gets `MODEL_BUSY` + `Retry-After` (`lab_policy = "reject"`, configurable to `queue`). | Measurement validity |
| DEC-13 | A profile may overlay process-level env (`process_env`) to allow one-variable experiments (TP §14). Effective env is part of the resident-unit identity. | TP §9, §14 |
| DEC-14 | `/v1/ensure` and `/v1/ensure/stream` are kept for Saltcode `ensure_resident()` compatibility; a header-authenticated POST stream is added; `?token=` only in compat mode. | BP §4.4 |
| DEC-15 | One binary, `saltnitor`, with subcommands (`daemon`, `tui`, CLI verbs). A `saltnitord` alias MAY be added. | BP §6.1 |
| DEC-16 | Phases are numbered P0–P11; P0 equals BP Phase 0. | Alignment |
| DEC-17 | The MoE cache "capacity" knob is abstract: the runtime exposes it as slots per layer (Codacus `--moe-cache-slots`) or as a size (e.g., upstream RFC `--moe-cache <MiB>`). Tuners search whichever integer the capability record names. | Dialects differ across forks (research, Sep 2026). |

### 7.1 Migration (MIG)

#### REQ-MIG-001 — Behavior inventory

### 7.4 Configuration (CFG)

#### REQ-CFG-001 — Config location
> MUST · Verify: T · Phase: P1 · Tasks: T1.7
- **AC1** The config loader SHALL use `$XDG_CONFIG_HOME/saltnitor/config.toml`, falling back to `~/.config/saltnitor/config.toml`, unless `--config <path>` is given. (T)
- **AC2** WHEN the daemon starts, it SHALL log the resolved config path. (T)
- **AC3** WHILE running under `sudo`, the config loader SHALL NOT silently switch to another user's config. (T)

#### REQ-CFG-002 — Missing config
> MUST · Verify: T · Phase: P1 · Tasks: T1.7 · Src: BP §4.5
- **AC1** WHEN no file exists at the default path and no `--config` is given, the process SHALL start with documented defaults and log that it did so. (T)
- **AC2** IF `--config` names a missing file, THEN the process SHALL exit with code 2. (T)

#### REQ-CFG-003 — Malformed config fails startup
> MUST · Verify: T · Phase: P1 · Tasks: T1.7 · Src: BP §4.5 · Fixes: BD-01 · INV-10
- **AC1** IF the config file exists but cannot be parsed or validated, THEN the process SHALL exit with code 2 before binding any port or spawning any process. (T)
- **AC2** WHEN AC1 happens, stderr SHALL name the file path, line and column, the dotted key path, the expected type/constraint, and the value found. Example: `ctx_size = "32768k"` under `[profiles.qwen36]` at line 42 reports `config.toml:42`, `profiles.qwen36.ctx_size`, `expected integer`, `found string "32768k"`. (T)
- **AC3** WHEN AC1 happens, the configured ports SHALL remain free and no child process SHALL exist. (T)

#### REQ-CFG-004 — Unknown keys
> MUST · Verify: T · Phase: P1 · Tasks: T1.7
- **AC1** IF a config contains an unknown key at any level, THEN the config loader SHALL reject it per REQ-CFG-003. (T)
- **AC2** The diagnostic SHOULD suggest the closest known key. (T)

#### REQ-CFG-005 — Schema versioning
> MUST · Verify: T · Phase: P1 · Tasks: T1.7 (AC2), T4.1 · Src: BP §4.5
- **AC1** WHERE `schema_version` is absent, the config loader SHALL treat the file as v1 and log a deprecation warning. (T)
- **AC2** IF `schema_version` is not a supported version, THEN the config loader SHALL fail with `CONFIG_INVALID`. (T)
- **AC3** v2 files SHALL declare `schema_version = 2`. (T)

#### REQ-CFG-006 — Semantic validation vs. environment state
> MUST · Verify: T · Phase: P4 · Tasks: T4.1, T4.9 · INV-10
- **AC1** IF the config has a semantic error (out-of-range port, profile referencing an undefined runtime, duplicate ID, invalid enum value, non-loopback listener with auth disabled), THEN startup SHALL fail with `CONFIG_INVALID`. (T)
- **AC2** IF a referenced runtime executable or model file is missing at startup, THEN the daemon SHALL still start, mark the runtime/profile unavailable (`RUNTIME_NOT_FOUND` / `MODEL_NOT_FOUND`), and show it in status, CLI, and TUI. (T)

#### REQ-CFG-007 — Path expansion
> MUST · Verify: T · Phase: P1 · Tasks: T1.7, T4.1
- **AC1** The config loader SHALL expand `~`, `$VAR`, and `${VAR}` in path-valued keys and resolve relative paths against the config file's directory. (T)
- **AC2** IF a path references an undefined variable, THEN the config loader SHALL fail with `CONFIG_INVALID`. (T)

#### REQ-CFG-008 — Separation of concerns
> MUST · Verify: I · Phase: P4 · Tasks: T4.1 · Src: BP §10, TP §7
- **AC1** Schema v2 SHALL separate `[daemon]`, `[security]`, `[storage]`, `[runtimes.<id>]` (+ `.env`), `[profiles.<id>]`, `[remote]`, `[scheduler]`, `[oracle]`, `[telemetry]`. (I)
- **AC2** Generated data (DB, benchmarks, traces, MoE profiles, crash records, generated presets) SHALL live under `storage.data_dir` or the state dir — never in runtime checkouts or the config dir. (I)

#### REQ-CFG-009 — Profile sources and IDs
> MUST · Verify: T · Phase: P4 · Tasks: T4.1 · Src: TP §7, §10
- **AC1** The config loader SHALL accept profiles inline (`[profiles.<id>]`) and as files `profiles/<id>.toml` next to `config.toml`. (T)
- **AC2** IF a profile ID does not match `^[a-z0-9][a-z0-9._-]{0,63}$`, or the same ID is defined twice, THEN the config loader SHALL fail with `CONFIG_INVALID`, naming both locations for duplicates. (T)

#### REQ-CFG-010 — Migration v1 → v2
> MUST · Verify: T · Phase: P4 · Tasks: T4.6, T11.2
- **AC1** WHEN the operator runs `saltnitor config migrate [--router-ini <path>]`, the CLI SHALL write a v2 config in which every router section becomes a profile, keys map to registry params or `extra_args`, and the result validates. (T)
- **AC2** `[PROP]` For any valid v1 config plus router INI, the preset generated from the migrated v2 config SHALL be semantically equal to the original INI (same sections, same key/values). (T)
- **AC3** The CLI SHALL back up the original files before writing. Nothing SHALL rewrite config files implicitly; loading a v1 file converts it in memory only (REQ-MIG-007/AC7). (T)

#### REQ-CFG-011 — Live reload
> SHOULD · Verify: T · Phase: P4 · Tasks: T4.2
- **AC1** WHEN the daemon receives `SIGHUP` or `saltnitor config reload`, it SHOULD validate the new config completely before applying it. (T)
- **AC2** IF the new config is invalid, THEN the daemon SHOULD keep the running config and report the error in status and logs. (T)
- **AC3** Settings that need a restart SHOULD be reported as pending. (T)

#### REQ-CFG-012 — Safe writes
> MUST · Verify: T · Phase: P4 · Tasks: T4.6, T4.15
- **AC1** WHEN Saltnitor writes a config, profile, or generated preset, it SHALL write atomically (temp file in the same dir → fsync → rename) and keep one `.bak`. (T)
- **AC2** `[PROP]` For any TOML file edited by the tuner, comments, ordering, and unrelated keys SHALL be preserved byte-for-byte outside the edited values. (T)

#### REQ-CFG-013 — Config check
> MUST · Verify: T · Phase: P3 · Tasks: T3.1
- **AC1** WHEN the operator runs `saltnitor config check [--config <path>]`, the CLI SHALL validate without starting services, print the effective config with secrets redacted, and exit 0 (valid) or 2 (invalid). (T)

### 7.5 Security (SEC)

#### REQ-SEC-001 — Centralized authentication
> MUST · Verify: T, I · Phase: P1 · Tasks: T1.9 · Src: BP §4.3 · Fixes: BD-03
- **AC1** The daemon SHALL enforce authentication and authorization in one middleware layer applied to the whole router, driven by the route policy table (Appendix A). Handlers SHALL contain no auth logic. (T, I)
- **AC2** `[PROP]` For every registered route, a request without valid credentials SHALL get the policy outcome (401 for protected routes), and a request with the wrong scope SHALL get 403. (T)
- **AC3** IF a route has no policy entry, THEN the route-enumeration test SHALL fail (default deny). (T)

#### REQ-SEC-002 — Auth defaults
> MUST · Verify: T · Phase: P1 · Tasks: T1.9 (AC3), T4.1, T9.2 · Src: BP §4.3, TP §37 · DEC-07
- **AC1** WHERE schema v2 is used, `security.require_auth` SHALL default to `true`. (T)
- **AC2** IF `require_auth = false` while any listener is neither loopback nor UDS, THEN startup SHALL fail with `CONFIG_INVALID`. (T)
- **AC3** WHERE schema v1 has a control token configured, the daemon SHALL enforce it on every protected route. (T)

#### REQ-SEC-003 — Secret sourcing
> MUST · Verify: T · Phase: P1 · Tasks: T1.10 (AC1, AC2, AC4), T4.1 · INV-16
- **AC1** The config loader SHALL read keys from environment variables (`*_env`) or files (`*_file`). (T)
- **AC2** IF a key file is readable by group or others, or not owned by the daemon user, THEN startup SHALL fail with `CONFIG_INVALID`. (T)
- **AC3** IF a v2 config contains a literal secret value, THEN startup SHALL fail with `CONFIG_INVALID`. (T)
- **AC4** WHERE a v1 config holds a literal `control_token`, the config loader SHALL accept it and log a deprecation warning. (T)

#### REQ-SEC-004 — Constant-time comparison
> MUST · Verify: I · Phase: P1 · Tasks: T1.9
- **AC1** The daemon SHALL compare tokens in constant time (e.g., the `subtle` crate). (I)

#### REQ-SEC-005 — Header auth; query tokens opt-in
> MUST · Verify: T · Phase: P1 · Tasks: T1.9, T6.5 · Src: BP §4.4 · Fixes: BD-04
- **AC1** The daemon SHALL accept credentials from `Authorization: Bearer`. (T)
- **AC2** IF a request carries `?token=` and `security.allow_query_token` is not `true`, THEN the daemon SHALL ignore the query token (a request with no other credentials gets 401). (T)
- **AC3** WHERE `allow_query_token = true`, the daemon SHALL accept `?token=` only on `GET /v1/ensure/stream`, log a startup warning, and redact the value everywhere. (T)

#### REQ-SEC-006 — Redaction and minimal logging
> MUST · Verify: T · Phase: P1 · Tasks: T1.10 (AC1), T6.6, T7.10 (AC2) · INV-16
- **AC1** Logs, crash records, status output, and exports SHALL NOT contain Authorization headers, tokens, or query-token values. (T)
- **AC2** Request logs SHALL store metadata only. Prompt and completion bodies SHALL be stored only while capture is explicitly enabled (REQ-BEN-012). (T)

#### REQ-SEC-007 — Admin scope
> MUST · Verify: T · Phase: P3 · Tasks: T3.3 (AC1), T9.2 · Src: BP §4.3 · DEC-10
- **AC1** The daemon SHALL authorize `/admin/*` only for a UDS peer with the daemon's UID or a request with an admin token. Inference keys SHALL never grant admin. (T)
- **AC2** WHERE `remote.allow_admin` is not `true`, admin routes SHALL NOT be registered on remote listeners (404 there). (T)

#### REQ-SEC-008 — UDS protection
> MUST · Verify: T · Phase: P3 · Tasks: T3.3
- **AC1** The daemon SHALL create `$XDG_RUNTIME_DIR/saltnitor/` with mode 0700 and the socket with mode 0600. (T)
- **AC2** IF a UDS peer's credential UID differs from the daemon UID, THEN the daemon SHALL reject the connection. (T)

#### REQ-SEC-009 — Upstream isolation
> MUST · Verify: T · Phase: P3 · Tasks: T3.5 (AC1), T9.3 · Src: BP §15, TP §37 · INV-07
- **AC1** WHILE in managed mode, the runtime manager SHALL bind the runtime to `127.0.0.1` only. (T)
- **AC2** The runtime manager SHOULD start the runtime with a random per-start upstream API key held only in daemon memory, so local processes cannot drive loads by bypassing the scheduler. (T)

#### REQ-SEC-010 — No root
> MUST · Verify: T, D · Phase: P3 · Tasks: T3.3 · Src: BP §6.2
- **AC1** The daemon, TUI, and CLI SHALL run fully as a normal user. (D)

#### REQ-SEC-011 — Failed-auth audit

- **AC1** WHEN authentication fails, the daemon SHOULD log listener, peer address, route, and key-label hint, rate-limited to at most one line per peer per second. (T)

#### REQ-SEC-012 — No credential forwarding

#### REQ-SEC-013 — Remove hardcoded credentials
> MUST · Verify: I · Phase: P1 · Tasks: T1.6 · Fixes: BD-07
- **AC1** Code, scripts, and docs SHALL contain no literal credentials. The TUI SHALL use the configured client key. (I)

#### REQ-SEC-014 — Labeled keys

### 7.7 OpenAI-compatible proxy (PRX)

#### REQ-PRX-001 — Routes

> MUST · Verify: T, I · Phase: P1 · Tasks: T1.11 · Src: BP §4.2, §14 · Fixes: BD-02 · INV-08

#### REQ-PRX-003 — Byte-exact bodies
> MUST · Verify: T · Phase: P1 · Tasks: T1.11, T10.10 · Src: BP §14 · INV-01
- **AC1** `[PROP]` For any upstream response (streaming or not, any chunking, including SSE comments, keep-alives, `data: [DONE]`, tool-call deltas, reasoning fields), the downstream body bytes SHALL equal the upstream body bytes. (T)

#### REQ-PRX-004 — Status and header preservation
> MUST · Verify: T · Phase: P1 · Tasks: T1.11
- **AC1** The proxy SHALL return the upstream status code and preserve end-to-end headers (including `Content-Type` and `Cache-Control`). (T)
- **AC2** The proxy SHALL drop the RFC 9110 §7.6.1 hop-by-hop headers (`Connection`, `Keep-Alive`, `Proxy-Connection`, `TE`, `Trailer`, `Transfer-Encoding`, `Upgrade`) and add `X-Request-Id`. (T)

#### REQ-PRX-005 — Request forwarding
> MUST · Verify: T · Phase: P1 · Tasks: T1.11 · INV-01
- **AC1** The proxy SHALL forward request body bytes unmodified; only headers may change (REQ-SEC-012, REQ-PRX-004, REQ-PRX-009). (T)
- **AC2** The `model` value SHALL be the profile ID and SHALL equal the upstream preset section or `--alias` (DEC-03), so no body rewrite is needed. (T)

#### REQ-PRX-006 — Cancellation propagation
> MUST · Verify: T · Phase: P1 · Tasks: T1.12 · Src: BP §14
- **AC1** WHEN the client disconnects, the proxy SHALL abort the upstream request within `cancel_propagation_ms`. The fake runtime observes the close, and the active-request count returns to its prior value. (T)

#### REQ-PRX-007 — Admission pipeline
> MUST · Verify: T, I · Phase: P6 · Tasks: T6.3 · Src: TP §30, BP §14 · Fixes: BD-19
- **AC1** The proxy SHALL process each request in order: authenticate → validate → resolve profile (404 `MODEL_NOT_FOUND`) → scheduler lease (queue or reject) → oracle admission at swap time when a swap is needed → runtime health → forward. (T)
- **AC2** IF any step fails, THEN no bytes SHALL reach the upstream for that request. (T)
- **AC3** The TUI hot-swap and interrogator SHALL use this same path; no TUI code SHALL call the runtime directly. (I)

#### REQ-PRX-008 — Error provenance
> MUST · Verify: T · Phase: P1 · Tasks: T1.12
- **AC1** WHEN the upstream returns 4xx/5xx, the proxy SHALL pass the response through byte-exact with its status. (T)
- **AC2** IF the upstream response is malformed or reset before headers, THEN the proxy SHALL return 502 `RUNTIME_UNHEALTHY` in the ERR envelope. (T)

#### REQ-PRX-009 — Request IDs
> MUST · Verify: T · Phase: P1 · Tasks: T1.11
- **AC1** WHEN a request carries `X-Request-Id` matching `^[A-Za-z0-9._-]{1,128}$`, the proxy SHALL keep it; otherwise it SHALL generate one (UUIDv7 or ULID). (T)
- **AC2** The proxy SHALL echo the ID in the response header, forward it upstream, and include it in logs, request history, and error bodies. (T)

#### REQ-PRX-010 — Timeout policy
> MUST · Verify: T · Phase: P1 · Tasks: T1.12
- **AC1** The proxy SHALL apply the configurable connect, first-byte, and idle-between-chunks timeouts (§6), with no total deadline for streams by default. (T)
- **AC2** IF a timeout fires before response headers are sent, THEN the proxy SHALL return 504 `UPSTREAM_TIMEOUT`. (T)

#### REQ-PRX-011 — Mid-stream failure
> MUST · Verify: T · Phase: P1 · Tasks: T1.12
- **AC1** IF the upstream fails after response headers were sent, THEN the proxy SHALL end the downstream response without a synthetic `data: [DONE]` or any fabricated content, and record `UPSTREAM_STREAM_ABORTED` with the request ID. (T)

#### REQ-PRX-012 — Graceful shutdown
> MUST · Verify: T · Phase: P3 · Tasks: T3.8
- **AC1** WHEN the daemon receives SIGTERM or SIGINT, the proxy SHALL stop accepting connections, let in-flight requests finish for up to `shutdown_grace_ms`, then abort the rest per REQ-PRX-011 and release their leases. (T)

#### REQ-PRX-013 — Observational metrics
> MUST · Verify: T · Phase: P6 · Tasks: T6.6
- **AC1** For each request, the proxy SHALL record TTFT (first upstream body byte after forwarding), duration, bytes, status, and — when present in the payload — `usage` and llama.cpp `timings` (prompt/predicted counts and rates, draft counts). (T)
- **AC2** `[PROP]` Metric extraction SHALL read a copy of the forwarded bytes (tee) and SHALL NOT change or delay what is forwarded. (T)

#### REQ-PRX-014 — `/v1/models`
> MUST · Verify: T · Phase: P4 · Tasks: T4.9 · Src: TP §31 · Fixes: BD-28
- **AC1** WHEN `GET /v1/models` is requested, the proxy SHALL return `{"object":"list","data":[{"id":"<profile>","object":"model","owned_by":"saltnitor"}]}` for profiles with `serve = true` whose runtime and model are available. (T)
- **AC2** IF a profile is unavailable or `serve = false`, THEN it SHALL be omitted here; unavailable profiles are listed in `/v1/status` with reasons. (T)
- **AC3** The proxy SHALL NOT surface upstream-internal model IDs that are not profiles (e.g., a phantom `default` preset entry). (T)

#### REQ-PRX-015 — `/v1/status`
> MUST · Verify: T · Phase: P3 · Tasks: T3.2, T4.9, T5.11, T6.6, T9.1 · Src: TP §34
- **AC1** WHEN an authenticated client requests `GET /v1/status`, the daemon SHALL return JSON containing `daemon_state`, `version`, `api_version`, `runtime` (id, mode, commit, binary-hash prefix, health), `resident` (profile, unit state, since), and `telemetry` (VRAM/RAM used/total, GPU util). (T)

Until then a section SHALL be absent, not filled with placeholder values (INV-18). (T)

#### REQ-PRX-016 — `/healthz`

Stopping the runtime goes through the runtime lifecycle instead. (T)

#### REQ-PROC-006 — No name-based kill

#### REQ-PROC-007 — GPU processes with PID

- **AC1** GPU process listings SHALL include the PID and per-process GPU memory, from NVML or `nvidia-smi --query-compute-apps=pid,process_name,used_memory`. IF per-process memory is unavailable, THEN the value SHALL be `null` with a reason (INV-18). (T)

#### REQ-PROC-008 — Emergency runtime stop
> MUST · Verify: T, D · Phase: P3 · Tasks: T3.5 · Src: BP §4.6
- **AC1** WHEN emergency stop is invoked (TUI Ctrl+K, CLI, API), the daemon SHALL stop the runtime through its lifecycle owner — managed: SIGTERM, then SIGKILL after grace, to the process group; external: `systemctl stop` — and report VRAM before and after. (T, D)

### 7.16 Oracle v2 (ORC)

#### REQ-ORC-001 — Prediction hierarchy
> MUST · Verify: T · Phase: P5 · Tasks: T5.9 · Src: BP §12.1
- **AC1** The oracle SHALL try `EXACT_OBSERVED` → `INTERPOLATED` → `GGUF_ESTIMATE` → `HEURISTIC` → `UNKNOWN` in order, use the first that applies, and record the tier in the decision. (T)
- **AC2** `INTERPOLATED` SHALL apply only when ≥ 2 observations share the model hash, runtime binary hash, and every non-numeric memory param, and the target lies within the observed range of each varied numeric param. It never extrapolates. (T)

#### REQ-ORC-002 — Configuration hash
> MUST · Verify: T · Phase: P5 · Tasks: T5.6 · Src: BP §12.2
- **AC1** The oracle SHALL compute the config hash as SHA-256 over canonical JSON (sorted keys, normalized values) of the model file hash, the runtime binary hash plus capability set, and every registry param flagged memory-relevant. (T)
- **AC2** `[PROP]` The hash SHALL NOT depend on key order, and it SHALL change whenever any memory-relevant param changes. (T)

#### REQ-ORC-003 — Model hash cache
> MUST · Verify: T · Phase: P5 · Tasks: T5.5
- **AC1** The oracle SHALL cache each model file's SHA-256 keyed by (path, size, mtime_ns, inode), recompute it when any key part changes, and hash in the background with progress. (T)
- **AC2** WHILE a hash is pending, profiles SHALL remain usable with the `GGUF_ESTIMATE` or `HEURISTIC` tier. (T)

#### REQ-ORC-004 — Observed store
> MUST · Verify: T · Phase: P5 · Tasks: T5.7 · Src: BP §12.3
- **AC1** Per config hash, the oracle SHALL persist startup VRAM/RAM, context VRAM after filling ctx, peak VRAM/RAM, sample count, first/last seen, the `stable` flag, and failures (crash IDs). (T)
- **AC2** WHEN the daemon restarts, a previously observed configuration SHALL be predicted as `EXACT_OBSERVED`. (T)

#### REQ-ORC-005 — Admission formula
> MUST · Verify: T · Phase: P5 · Tasks: T5.10 · Src: BP §12.4 · Fixes: BD-13
- **AC1** The oracle SHALL compute `allocatable_vram = total_vram − (used_vram − runtime_tree_vram) − reserve_vram` and `allocatable_ram = MemAvailable + runtime_tree_RssAnon − reserve_ram`. File-backed pages are already reflected in `MemAvailable`. (T)
- **AC2** The oracle SHALL admit only when predicted VRAM ≤ allocatable VRAM and predicted RAM ≤ allocatable RAM. (T)
- **AC3** WHEN telemetry reports total 12 288 MB, used 3 000 MB (runtime 2 500 MB), and reserve 800 MB, allocatable VRAM SHALL be 10 988 MB. (T)
- **AC4** WHEN external usage rises by 2 048 MB, a 10 000 MB prediction SHALL flip from admitted to `ORACLE_REJECTED`. (T)
- **AC5** `[PROP]` Admission SHALL be monotonic: raising external usage or the reserve never turns a rejection into an admission. (T)

#### REQ-ORC-006 — Confidence and risk
> MUST · Verify: T · Phase: P5 · Tasks: T5.10 · Src: BP §12.5
- **AC1** Every decision SHALL expose its confidence tier and a risk: headroom ≥ `risk.low_mb` → LOW; ≥ `risk.medium_mb` → MEDIUM; ≥ 0 → HIGH (admitted, with a warning); < 0 → REJECT. (T)

#### REQ-ORC-007 — GGUF estimate
> MUST · Verify: T · Phase: P5 · Tasks: T5.8 · Src: BP §12.1
- **AC1** The oracle SHALL parse GGUF metadata and the tensor table and estimate VRAM = GPU-placed weights (given ngl, n_cpu_moe, override-tensor rules) + KV (per-layer attention layout from metadata, ctx × parallel, KV types) + MoE cache capacity × per-unit size + a per-architecture overhead constant, calibrated from observations with a conservative default. It SHALL estimate RAM = CPU-placed weights, plus pinned buffers when host registration is on. (T)
- **AC2** IF the architecture's layout is unknown, THEN the oracle SHALL skip to `HEURISTIC`. (T)

#### REQ-ORC-008 — Heuristic fallback
> MUST · Verify: T · Phase: P5 · Tasks: T5.9 · Src: BP §12
- **AC1** The existing filename heuristic (`parse_params_b`/`parse_bpw`) SHALL CONTINUE TO exist, only as the `HEURISTIC` tier. (T)

#### REQ-ORC-009 — Predicted vs. actual
> MUST · Verify: T, A · Phase: P5 · Tasks: T5.11, T5.13 · Src: BP §29
- **AC1** WHEN a load or benchmark completes, the oracle SHALL store the predicted and measured peaks and the error percentage, and the UI SHALL display them. (T)
- **AC2** At G5, errors on the reference host SHALL be within `oracle.accuracy_pct` for each tier, or the operator SHALL accept revised targets in writing. (A) `[HW]`

#### REQ-ORC-010 — Swap-time evaluation
> MUST · Verify: T · Phase: P5 · Tasks: T5.10, T6.3
- **AC1** WHEN a swap is about to execute, the oracle SHALL evaluate admission with the telemetry current at that moment, not the telemetry from when the request was queued. (T)

#### REQ-ORC-011 — Rejection details
> MUST · Verify: T · Phase: P5 · Tasks: T5.10 · Src: BP §23
- **AC1** `ORACLE_REJECTED.details` SHALL contain `required_mb`, `available_mb`, `headroom_mb`, `confidence`, `risk`, `config_hash`, `reason`, and the inputs (total, used, runtime share, reserve). (T)

#### REQ-ORC-012 — Force
> MUST · Verify: T · Phase: P5 · Tasks: T5.10 · Src: BP §13.3
- **AC1** IF a force override comes without admin scope, THEN the daemon SHALL return 403 `AUTH_FORBIDDEN`. (T)
- **AC2** WHEN an admin forces, the daemon SHALL log it and record the outcome (OOM or success) against the config hash. (T)

#### REQ-ORC-013 — Known-failed configurations
> MUST · Verify: T · Phase: P5 · Tasks: T5.12 · Src: TP §36
- **AC1** WHEN a configuration hits `GPU_OOM`, the oracle SHALL mark its hash failed and reject later admissions (`reason = "known_failed"`) unless forced, until a later stable run clears the mark. (T)

#### REQ-ORC-014 — Stability semantics
> MUST · Verify: T · Phase: P5 · Tasks: T5.7, T8.5 · INV-05
- **AC1** The oracle SHALL set `stable = true` only after the validation workload (`tuner.validation_sequence` or the profile's own) completes without OOM or crash. Load success alone SHALL NOT set it. (T)

#### REQ-ORC-015 — UNKNOWN
> MUST · Verify: T · Phase: P5 · Tasks: T5.9
- **AC1** IF the prediction tier is `UNKNOWN`, THEN the oracle SHALL reject unless forced. (T)

### 7.17 Residency scheduler (SCH)

#### REQ-SCH-001 — Leases
> MUST · Verify: T · Phase: P6 · Tasks: T6.1 · Src: BP §13.2
- **AC1** The scheduler SHALL give every forwarded request a lease on the resident unit, held from forwarding until the response completes or aborts. `active_requests` equals the number of leases. (T)

#### REQ-SCH-002 — No swap under lease
> MUST · Verify: T · Phase: P6 · Tasks: T6.1, T6.3 · Src: BP §13, §29 · Fixes: BD-19, BD-23
- **AC1** `[PROP]` For any interleaving of arrivals, completions, and cancellations, the scheduler SHALL NOT swap or unload the resident unit while `active_requests > 0`, except by admin force. (T)
- **AC2** WHEN an admin forces a swap, the scheduler SHALL abort the leases per REQ-PRX-011 and log the action. (T)

#### REQ-SCH-003 — Policies
> MUST · Verify: T · Phase: P6 · Tasks: T6.4 · Src: BP §13.3
- **AC1** The scheduler SHALL support `scheduler.policy ∈ {queue (default), reject}`, with force available to admins only. (T)
- **AC2** WHILE `policy = reject`, a request for a non-resident unit while leases are active SHALL get 503 `MODEL_BUSY` with `Retry-After`. (T)

#### REQ-SCH-004 — Fair queue
> MUST · Verify: T · Phase: P6 · Tasks: T6.1, T6.4
- **AC1** `[PROP]` Within a unit, requests SHALL be admitted in FIFO order. (T)
- **AC2** WHEN a request for a non-resident unit is queued, new requests for the resident unit SHALL queue behind it (swap-pending barrier). (T)
- **AC3** IF the queue holds `queue.max_len` requests, or a request waits `queue.max_wait_ms`, THEN the scheduler SHALL reject it with `MODEL_BUSY` (`details.reason = "queue_full" | "queue_timeout"`). (T)
- **AC4** `[PROP]` No request SHALL wait longer than `queue.max_wait_ms` without a decision. (T)

#### REQ-SCH-005 — Batching
> MUST · Verify: T · Phase: P6 · Tasks: T6.1
- **AC1** WHEN a swap to unit B completes, the scheduler SHALL admit every request for B that was queued before the swap began before starting another swap. (T)

#### REQ-SCH-006 — In-flight cap
> MAY · Verify: T · Phase: P6 · Tasks: T6.4
- **AC1** WHERE a profile sets `max_inflight`, the scheduler MAY queue requests beyond it. The default is unlimited (llama-server queues on its slots). (T)

#### REQ-SCH-007 — Request identity and metrics
> MUST · Verify: T · Phase: P6 · Tasks: T6.6 · Src: BP §13.4
- **AC1** For each request, the scheduler SHALL record request ID, client (key label, peer address, User-Agent), profile, runtime, start time, queue wait, stream flag, TTFT, duration, prompt/completion tokens (when reported), and status/error code in `request_log`. (T)
- **AC2** Records older than `request_log.retention_days` SHALL be deleted. (T)
- **AC3** `/v1/status` SHALL include aggregates (counts, error rate, TTFT percentiles) over a recent window. (T)
- **AC4** WHERE `daemon.metrics_endpoint = true`, the daemon SHOULD expose an authenticated Prometheus `/metrics` endpoint (OQ-06). (T)

#### REQ-SCH-008 — Lab lease
> MUST · Verify: T · Phase: P6 · Tasks: T6.7 · DEC-12
- **AC1** WHEN a benchmark, trace, or tuner starts, the scheduler SHALL grant an exclusive lab lease only after active leases drain. (T)
- **AC2** WHILE a lab lease is held and `lab_policy = reject`, inference SHALL get `MODEL_BUSY` (`reason = "lab"`) with `Retry-After`. (T)
- **AC3** WHEN the lab lease is released, the scheduler SHALL restore the pre-lab resident unit, or the fallback profile. (T)

#### REQ-SCH-009 — Residency state machine
> MUST · Verify: T · Phase: P6 · Tasks: T6.2 · Src: BP §26
- **AC1** Unit states SHALL be `UNLOADED`, `LOADING`, `READY`, `DRAINING`, `UNLOADING`, `FAILED`, with only the transitions in Appendix E. Every other transition SHALL be rejected, and a test SHALL cover the full transition table. (T)

#### REQ-SCH-010 — Residency scenario
> MUST · Verify: T · Phase: P6 · Tasks: T6.3 · Src: BP §26
- **AC1** WHEN A is streaming and B is requested, B SHALL queue; WHEN A completes, B SHALL load and then be served. A's response SHALL be complete and byte-exact. (T)

#### REQ-SCH-011 — Crash handling
> MUST · Verify: T · Phase: P6 · Tasks: T6.3, T9.4
- **AC1** IF the runtime crashes while leases are held, THEN the scheduler SHALL release the leases, end the affected requests per REQ-PRX-011 or with ERR errors, and hand the state to recovery (REQ-SVC-006/007). (T)

#### REQ-SCH-012 — Pure core
> MUST · Verify: T · Phase: P6 · Tasks: T6.1
- **AC1** The scheduler's decisions SHALL come from a pure, I/O-free state machine (events in, actions out), exercised by property tests for REQ-SCH-002/AC1 and REQ-SCH-004/AC1, AC4. (T)

### 7.18 Benchmark lab (BEN)

#### REQ-BEN-001 — Benchmark classes
> MUST · Verify: T · Phase: P7 · Tasks: T7.3, T7.4, T7.9 · Src: BP §19.1, TP §21

## Appendix E — State machines

**Daemon** (`daemon_state`): `STARTING → READY`; `READY ⇄ MODEL_LOADING`; `MODEL_LOADING → OOM_RECOVERY → MODEL_LOADING (fallback) → READY`; `READY | MODEL_LOADING → DEGRADED` (runtime unhealthy, remote listener missing, recovery in progress) `→ READY`; any → `CRASHED` (crash-loop guard); `CRASHED → STARTING` (manual start). Clients show `OFFLINE` when the daemon is unreachable.

**Resident unit:** `UNLOADED → LOADING → READY → DRAINING → UNLOADING → UNLOADED`; `LOADING → FAILED`; `READY → FAILED` (crash); `FAILED → UNLOADED` (cleanup). Router status mapping: `unloaded`/`sleeping` → `UNLOADED`; `loading`/`downloading` → `LOADING`; `loaded` → `READY`; `failed` → `FAILED`.

## Appendix H — Glossary

- **Resident unit** — (runtime id, effective-env hash, profile id) currently loaded and serving.
- **Lease** — a request's claim on the resident unit while it is forwarded and streamed. **Lab lease** — the exclusive claim held by benchmarks, traces, and tuners.
- **Profile** — a named, validated configuration: runtime + model + params + env overlay. **Resolved profile** — the fully expanded args, env, model hash, and runtime fingerprint actually used.
- **Runtime / channel** — a configured llama.cpp build; the channels are `upstream`, `codacus-stable`, `codacus-testing`.
- **Capability** — a runtime feature proven by a probe or declared by override, with provenance and variant.
- **Fingerprint** — identity of a runtime build (commit, hashes, compiler, CUDA, capabilities).
- **Config hash** — hash of the memory-relevant configuration; the key for observed memory.
- **Validation workload** — the sequence a configuration must survive to be `stable`.
- **Fallback profile** — the known-safe profile used for recovery. **Production profile** — the profile promoted, with evidence, for daily agent use.
- **Ladder** — ordered, one-variable-per-stage tuning experiment (TP §14).
- **Gate** — end-of-phase acceptance; a phase is complete only when its gate passes. **Evidence file** — `docs/specs/vnext/evidence/G<n>.md`.
- **Runtime falsification** — exercising a claimed feature through the running product's real surface to try to prove it does *not* work; the outcome is `NOT_FALSIFIED` or `FALSIFIED`.
