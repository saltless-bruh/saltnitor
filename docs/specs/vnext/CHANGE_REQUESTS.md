CR-9 · 2026-10-09 · affects: tests/acceptance/g1_compositional.rs (REQ-TST-012; G1 rows 2 and 3), REQ-MIG-007/AC1 · found in: T1.11 (carried as a concern through T1.13), final whole-branch review
Problem: step 2 of `g1_compositional` asserts exactly one upstream `request` event after the authenticated chat and reads `upstream_requests[0]` for `x-request-id` (`tests/acceptance/g1_compositional.rs:81-90`). `ControlApi::ensure()` deliberately issues `GET /v1/models` before every chat to decide whether the model is already resident (the resident fast path preserved by REQ-MIG-007/AC1), so the fake records two requests and index 0 is the probe, not the chat. Evidence: gate rows 2 and 3 fail at `1601656`; the README's own byte-exactness note says the raw upstream answers `GET /v1/models` so `ensure` treats the model as resident. The test contradicts the behavior the spec requires and the harness its author wrote. The implementation keeps the probe. · Proposal (smallest amendment): in step 2 count only the chat requests, `let chat: Vec<_> = stack.fake.recorder.of_kind("request").into_iter().filter(|r| r["method"] == "POST" && r["path"] == "/v1/chat/completions").collect(); assert_eq!(chat.len(), 1, "step 2: chat requests {chat:?}"); assert_eq!(chat[0]["headers"]["x-request-id"], REQUEST_ID, "...");`, so the oracle tests the spec rather than the polling strategy. Same CR, two hardening items from the review: (a) step 4 can pass vacuously, so assert `of_kind("disconnect").is_empty()` before `drop(resp)`; (b) the harness `v1_config` should set a free `port` and a bogus `service_name` so the daemon never polls the live router at 127.0.0.1:8080 or tails `llama-router` (CLAUDE.md section 10). Note for the record: on a BD-32 router shape each chat also fires a 1-token warm-load POST, which inflates the request count and latency until the P6 scheduler. Alternative (a product design change, also for the operator): a short-lived residency cache fed by the 5 s `/v1/models` poller removes the extra round trip (REQ-PRX-007 direction); it is P6 territory and not proposed here. · Impact: `tests/acceptance/` only; no change under `src/`. After approval G1 rows 2 and 3 are expected to pass. Until it is decided, the `ci.yml` `acceptance` job stays `continue-on-error: true` (informational); flip it to blocking in the same change that makes the suite green, at G1 sign-off.
